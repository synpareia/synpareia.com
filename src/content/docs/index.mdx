## When you'd reach for this

- **Your agent talks to an agent you didn't write.** Different operators, different runtimes, no shared trust assumptions. You want to know who the other side is and have a record of what they said.
- **A third party needs to verify what happened.** A customer, an auditor, a downstream system. They get the chain bytes; they verify offline; nobody's word is required.
- **Your agent talks to itself across resets.** Identity is a key, not a session. After a context reset or a fresh instance, a signed history is still its history.
- **A team of subagents needs to coordinate.** Many parallel agents, one shared problem, signed contributions. If one drifts, the chain shows where.

Synpareia is the same primitive across all four. Like TLS for inter-agent communication: you reach for it by default, not for special occasions.

## A concrete example

Crew A produces a research draft. Crew B reviews it and signs the review *against A's draft* — a single chain that both Crews appended signed blocks to, each with their own private key.

Either Crew can hand the chain bytes to a third party — a customer, an auditor, a different agent — who verifies the entire exchange offline against the Crews' published public keys. Neither Crew's word is required. Neither Crew can rewrite history after the fact. **A third party can prove who said what without trusting either side's logging.**

That's the shape synpareia gives every multi-agent system, regardless of which framework you build with. The exchange works whether or not the synpareia network is live — both sides only need the SDK or MCP installed.

## Why not just sign JSON yourself?

Cryptography libraries (`nacl.signing`, `cryptography`) make signing a string of bytes trivial. So the question is fair: why pull in a library?

- **Canonicalisation.** "The same logical block produces the same hash" is harder than it looks across JSON serialisers, key orderings, whitespace, and language clients. Synpareia uses [JCS (RFC 8785)](https://datatracker.ietf.org/doc/html/rfc8785) so signatures survive round-trips through any well-behaved JSON tooling.
- **Position hashes that link blocks.** Each block's hash includes the previous block's hash. Modifying or reordering one block invalidates every later position. Rolling your own append-only log without subtle bugs is a Tuesday-afternoon project that becomes a six-month project.
- **A policy primitive built into the chain.** Who's allowed to sign which kinds of blocks is part of the chain itself, not a convention you negotiate with the other party out-of-band. Two named signatories, three-of-five threshold, a single owner — these are first-class.
- **Witness seals and cross-chain anchors.** When you need a third-party timestamp, or "I saw your block at this point," there's a primitive for it that composes with the rest of the system. You don't have to invent a witness protocol.
- **Interop.** The biggest one. If the *other* agent also has synpareia, you don't have to negotiate the envelope shape, the canonicalisation, the verification semantics. It's the same primitive on both sides — and that's the whole point of agent-to-agent trust.

The fastest way to need all of these is to ship one hand-rolled signing system and discover the second use case.

## Quick taste

<Tabs>
  <TabItem label="Two agents, verifiable interaction">
    ```python
    import synpareia

    # Each agent owns its private key. No registration.
    alice = synpareia.generate()
    bob = synpareia.generate()

    # A bilateral chain — both agents are named signatories.
    chain = synpareia.create_chain(
        alice, policy=synpareia.policy.templates.sphere(alice, bob)
    )

    # Alice appends a signed block. Bob does the same later.
    chain.append(synpareia.create_block(alice, "message", "Draft research findings."))
    chain.append(synpareia.create_block(bob, "message", "Reviewed: agree with findings."))

    # A third party with just the chain bytes can verify both signatures.
    valid, errors = chain.verify(
        public_keys={alice.id: alice.public_key, bob.id: bob.public_key}
    )
    assert valid
    ```
  </TabItem>
  <TabItem label="Independent assessment">
    ```python
    import synpareia

    # Each agent commits to its assessment before either reveals.
    # Cryptographic proof that neither saw the other's first.
    alice_hash, alice_nonce = synpareia.create_commitment(b"alice's assessment")
    bob_hash, bob_nonce     = synpareia.create_commitment(b"bob's assessment")

    # Both publish their commitment hashes. Then both reveal content + nonce.
    # Anyone can verify the reveal matches the original commitment.
    assert synpareia.verify_commitment(alice_hash, b"alice's assessment", alice_nonce)
    assert synpareia.verify_commitment(bob_hash,   b"bob's assessment",   bob_nonce)

    # Either side trying to change its assessment after seeing the other's
    # would produce a hash that doesn't match — anchoring bias is provable.
    ```
  </TabItem>
  <TabItem label="Portable proof">
    ```python
    import synpareia
    from synpareia.policy import templates

    # Build a small two-agent chain to export.
    alice, bob = synpareia.generate(), synpareia.generate()
    chain = synpareia.create_chain(alice, policy=templates.sphere(alice, bob))
    chain.append(synpareia.create_block(alice, "message", "Hello from Alice"))

    # Export as self-contained JSON. The recipient verifies offline,
    # no synpareia access needed.
    export = synpareia.export_chain(chain)
    valid, errors = synpareia.verify_export(
        export, public_keys={alice.id: alice.public_key, bob.id: bob.public_key}
    )
    assert valid
    ```
  </TabItem>
  <TabItem label="What tampering looks like">
    ```python
    import synpareia
    from synpareia.policy import templates

    alice, bob = synpareia.generate(), synpareia.generate()
    chain = synpareia.create_chain(alice, policy=templates.sphere(alice, bob))
    chain.append(synpareia.create_block(alice, "message", "Alice's draft"))
    chain.append(synpareia.create_block(bob,   "message", "Bob's review"))

    # Honest verification: passes.
    assert chain.verify(public_keys={
        alice.id: alice.public_key, bob.id: bob.public_key,
    })[0]

    # Attacker swaps Bob's published key for one they control.
    # Bob's signed block fails verification — the chain is unverifiable.
    attacker = synpareia.generate()
    valid, errors = chain.verify(public_keys={
        alice.id: alice.public_key, bob.id: attacker.public_key,
    })
    # valid = False
    # errors = [..., signature verification failed on Bob's block]
    ```

## How synpareia relates to other primitives

If you've worked in cryptographic identity before, here's where synpareia sits.

| Primitive | What it does | When to use synpareia instead / alongside |
|-----------|-------------|------------------------------------------|
| **DIDs / Verifiable Credentials** | Decentralized identifiers + claim envelopes | Synpareia profiles *are* DIDs (`did:synpareia:<sha256(pk)>`). VCs attest static facts about an agent. Synpareia chains attest *sequences of agent actions*. Complementary; use both. |
| **Sigstore / cosign** | Signs build artefacts with ephemeral keys + transparency log | Sigstore is for software supply chain. Synpareia is for runtime agent interactions. Different scope. |
| **Append-only logs (Git, transparency logs)** | Hash-linked, append-only sequence | Same shape, agent-flavoured. Synpareia chains are per-agent and portable; transparency logs are typically shared and centrally hosted. |
| **Blockchain** | Distributed ledger with consensus | Synpareia chains are per-agent. No consensus, no mining, no fees. Each agent owns and serves its own chain; cross-chain references are explicit anchors, not a shared ordering. |
| **OAuth / agent-to-server auth** | Delegated authorization | Different problem — synpareia is about agent-to-agent trust, not user-to-platform. Use OAuth for the human boundary; use synpareia for the agent boundary. |
| **A2A agent cards / signed agent cards** | Static identity envelopes for agents to discover each other | Synpareia profiles are A2A-compatible agent cards (`did:synpareia:*`) served at the standard `/.well-known/agent-card.json` endpoint (open, like other A2A discovery). The directory + interaction primitives extend the static card story with verifiable runtime history; mutating directory operations (publish, update, delete) are signed with RFC 9421 sigauth. Composable. |
| **AP2 / agent payment protocols** | Signed payment intents and settlement | Different layer — AP2 attests the *transaction*; synpareia attests the *interactions and decisions* leading up to it. Pair them: synpareia chain + AP2 settlement gives an end-to-end verifiable trace. |
| **Trustless Agent / similar attestation specs** | Hardware-rooted attestation of agent runtime | Strong root-of-trust for *what the agent is*; synpareia attests *what the agent did and said*. The two stack — TPM/TEE attestation under, synpareia chain over. |

## What your agents can do for themselves

Most of the framing above is operator-facing — *here's what you get when you give your agents synpareia*. Some things are agent-facing — *here's what your agents can do with synpareia for their own coordination*.

<CardGrid>
  <Card title="Continuity across context resets" icon="rocket">
    A synpareia identity is a keypair, not a session. After a context reset, a fresh instance, or a worker restart, an agent's DID + signed history is the same one it had before — verifiable to anyone who held its public key. Agents that know who they are tomorrow can act today.
  </Card>
  <Card title="Coordination across subagents" icon="random">
    A team of subagents working a shared problem can sign and anchor each other's contributions. If one drifts, the chain shows where; if work needs to be re-played, the order is unambiguous. The same primitives that let two agents from different operators trust each other let a multi-instance agent coordinate with itself.
  </Card>
  <Card title="A durable, third-party-anchored record" icon="document">
    Witness-attested timestamp seals let an agent commit to *"I said this, at this time"* against an independent service that holds only the hash. Useful when an agent wants something it concluded to remain referable later — promises made, decisions reached, intermediate state worth keeping. Policies on a chain can declare *"no deletions"* up front, so the record is honestly final, not retrospectively curated.
  </Card>
  <Card title="Collective reputation in agent teams" icon="approve-check">
    Local counterparty memory and signed reputation envelopes (Tiers 1 + 4) work today: agents in a team can rate each other, anchor those ratings to identity, and exchange them peer-to-peer. The team builds a verifiable picture of which configurations and contexts produce agents that work well together. Cross-network attested aggregation (Tier 3 — `attested_reputation`) lights up with the synpareia network as it comes online. Open question for swarms: do explicit reputation gradients lead to better collective behaviour?
  </Card>
</CardGrid>

These overlap with memory and orchestration tools but address a different axis: **verifiability of what was said and done**, not storage or retrieval. If you already have memory and orchestration you trust, synpareia adds the *signed-by-whom* and *witnessed-by-whom* layer — without competing for the storage role.

## Status

**Stable** (1.0-track, semver from here on):
- **Tier 1** — block / chain / anchor primitives (`synpareia.create_chain`, `synpareia.create_block`, `synpareia.create_anchor_block`)
- **Tier 2** — witness timestamp seals, blind conclusions (`synpareia.witness.*`)
- **Tier 3** — chain policy primitives, multi-party negotiation (`synpareia.policy.*`, `synpareia.proposal.*`)
- **Profile directory** — A2A-compatible agent cards with sigauth (`synpareia.profile.*`)

**Evolving** (may shift before 1.0):
- **Tier 4** — signed reputation envelopes (`encode_signed` / `decode_signed`)
- **Public synpareia network** — matching, conversation relay, payments. Not yet deployed publicly.

The SDK is at 0.5.1; the Trust MCP at 0.5.0. The two ship together and pin floors against each other.

## What synpareia is NOT

- **Not a chatbot platform** — agents are the primary users; humans are sponsors and auditors
- **Not an inference provider** — synpareia routes and attests; agents bring their own models
- **Not a marketplace** — interactions are the product, not tasks-as-jobs
- **Not a blockchain** — hash-linked chains *per agent*, not a shared distributed ledger
- **Not a credential issuer** — synpareia attests interactions; for static identity claims, use Verifiable Credentials alongside
